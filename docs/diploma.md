# Дипломный проект курса по QA Harness

## Назначение

Сначала создаём завершённый учебный продукт с проверяемым поведением, автоматизацией и рабочими инструкциями для агента. Затем получаем из него учебные версии: убираем конкретную возможность или проверку, сохраняя понятное задание и возможность оценить результат учащегося.

Текущий пример использует Go, Vue/TypeScript и Java-автоматизацию. Это одна реализация. Генератор должен сохранять требования и учебные цели при выборе других языков; код, команды и соглашения модулей будут различаться.

## Что уже решено

- Делаем полную версию перед сокращёнными учебными вариантами.
- Backend, frontend и язык автоматизации могут выбираться независимо в пределах возможностей генератора.
- Harness включает инструкции, skills, базу знаний, инструменты и проверку их работы на реальных задачах.
- Покрытие проверяется по требованиям и сценариям, с отдельным учётом фактического выполнения.
- Page Object, fluent, подготовка данных и отчётность входят в учебный материал; конкретная реализация зависит от стека.

## Предметная область — предложение, не утверждённый контракт

В исходном приложении найдены регистрация, вход, профиль, выход, удаление аккаунта, health и публичный список items. Новую предметную область пользователь пока не выбрал.

Рабочее предложение — каталог и личные коллекции. Альтернативы: трекер задач или развитие текущих items без переименования. Ниже описан возможный объём каталога; его нельзя выдавать за уже реализованные функции или согласованные детальные требования.

1. Учётная запись: регистрация, вход, профиль, выход, удаление собственной записи. Определить поведение после истечения сессии и при недоступности сервера; явно описать семантику JWT/logout.
2. Каталог: список, карточка, поиск, сортировка, пагинация, пустой результат и ошибка загрузки. Установить поля, ограничения и стабильный порядок результатов.
3. Личные коллекции: создать, переименовать и удалить коллекцию; добавить и убрать элемент каталога. Определить поведение повторного добавления и удаления отсутствующей связи.
4. Права доступа: владелец работает со своими коллекциями; другой пользователь и гость не получают чужие данные и не могут их изменить. Зафиксировать ответы API до реализации.
5. Изменения данных: сохранение в PostgreSQL, ограничения целостности, очистка связанных данных при удалении аккаунта, понятные ошибки при конфликте или недоступной БД.
6. Интерфейс: состояния загрузки/ошибки/пустого результата, валидация, отмена удаления, защита от повторной отправки, клавиатурная работа и доступные имена элементов. Если сохраняется RU/EN, новые экраны поддерживают оба языка.

Прежде чем программировать очередную функцию, её сценарии и ответы API записываются в `_contract/flows/` и OpenAPI. Предложения агента явно отделяются от исходных требований. Структура каталогов не заменяет архитектурное решение.

## Критерии готовности полной версии

- Приложение собирается и запускается из этого репозитория в изолированном локальном окружении. Данные переживают перезапуск. Документированы подготовка и очистка окружения.
- Для каждой принятой функции есть требования, существенные отрицательные и граничные сценарии, реализация и соответствующие проверки.
- Backend unit проверяют логику; integration используют настоящую отдельную БД; frontend component проверяют поведение интерфейса; API проверяют живое приложение; UI с mock проверяют контролируемые состояния; E2E проходят критические пользовательские пути через реальные части приложения.
- Для каждой проверки указано, что именно она доказывает. Один сценарий не дублируется на всех уровнях без причины. Нет требования иметь фиксированное число тестов или фиксированное соотношение уровней.
- Данные независимы между тестами. Ошибки cleanup видны и не скрывают исходное падение. Повторный запуск не стирает предыдущие результаты.
- Команды, состав выбранных тестов, результаты, пропуски и артефакты воспроизводимы. Локальное выполнение и CI учитываются отдельно; конфигурация pipeline не считается успешным запуском.
- Для заявленного «100%» указан конечный перечень сценариев и формула расчёта. Метрики кода измеряются отдельно; отсутствие дефектов не обещается.
- Отчёты читаемы, а опубликованные материалы не содержат секретов. Наличие фильтра редактирования не заменяет проверку реального результата.
- Доступность и другие ручные проверки имеют результат человека. Автоматически созданный чеклист остаётся чеклистом.
- Skills проверены на задачах запуска, добавления теста, диагностики и аудита покрытия. Зафиксировано поведение агента, а не только валидность файлов.
- Перед заявлением переносимости выполнена проверка хотя бы на другом сочетании языков. Полная поддержка матрицы требует проверки каждой заявленной комбинации или обоснованных ограничений генератора.

## База знаний

Входная точка — [docs/qa/README.md](qa/README.md). Общие материалы объясняют принципы; README модулей ведут к действующим примерам конкретного стека.

Знания должны развиваться вместе с реализацией. Нельзя удалять содержательные соглашения ради короткого `AGENTS.md` или объявлять частный стиль универсальным стандартом. При изменении примера проверяются связанные документы.

## Как получаем учебные версии

Для каждого задания фиксируются исходное состояние, требование, доступные учащемуся материалы, ожидаемые изменения и проверка результата. Рабочая полная версия сохраняется отдельно. Коммиты и теги создаются только по отдельной просьбе пользователя.

- Разработка: удалить реализацию одной согласованной функции; оставить спецификацию. Приёмочные проверки преподавателя хранить отдельно от выдачи учащемуся, если это предусмотрено заданием.
- Автоматизация: сохранить работающий продукт, убрать выбранные проверки. Учащийся анализирует риски, выбирает уровни и восстанавливает доказательства покрытия.
- Диагностика: внести конкретный воспроизводимый дефект. До выдачи убедиться, что предусмотренная проверка его обнаруживает, а исправленная версия проходит.
- Harness: убрать или ухудшить конкретную инструкцию/знание и задать наблюдаемую задачу агенту. Оценивать поведение и результат, а не объём написанной документации.

Сокращение не должно случайно ломать сборку, подготовку данных или несвязанные сценарии. После каждого изменения выполняется набор проверок именно этой учебной версии. Не называем версии новыми «уровнями пирамиды».

## Порядок работы

1. Восстановить базу знаний и получить исходные результаты запуска.
2. Выбрать предметную область и уточнить требования первой полной функции, включая права доступа и ошибки.
3. Реализовать функцию через backend, frontend и подходящие проверки. Обновить контракты, документацию и результаты.
4. Повторить для оставшегося согласованного функционала, затем проверить критерии готовности всего образца.
5. Подготовить обратные учебные задания и проверить каждую сокращённую версию.
6. Перенести проверенные решения в шаблоны генератора; подтвердить переносимость на заявленных стеках.

Полная версия пока не готова. Исходное состояние и выполненные проверки описаны в [baseline.md](baseline.md).
