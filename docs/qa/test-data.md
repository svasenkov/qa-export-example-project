# Тестовые данные и API-клиенты

Каждая проверка должна понимать происхождение своих данных и владеть изменяемыми ею сущностями. Независимый запуск и запуск в другом порядке не должны менять ожидаемый результат.

## Подготовка

Создавай изменяемые данные отдельно для теста. Общие учебные аккаунты пригодны только для сценариев, которые не меняют их состояние. Проверка удаления аккаунта должна создавать собственный аккаунт.

Для подготовки UI/E2E можно использовать API, когда создание данных через интерфейс не является предметом проверки. Если проверяется регистрация через UI, предварительная регистрация того же пользователя через API подменяет сценарий.

Используй существующий builder или фабрику, если они подходят. Данные должны быть воспроизводимы настолько, чтобы восстановить причину сбоя: сохраняй безопасный идентификатор сценария, но не пароли и токены. Границы и недопустимые значения задавай явно, а не надейся случайно получить их из генератора.

## Клиенты

Клиент централизует адреса, сериализацию и повторяющиеся операции. Адрес стенда берётся из конфигурации выбранного модуля. Клиент подготовки может требовать успешный статус. Для проверки ошибки используй интерфейс, позволяющий получить отрицательный ответ: helper, который всегда требует `200`, для этого не подходит.

При проверке прав доступа создай двух разных пользователей. Успех владельца не доказывает запрет для другого пользователя или гостя. Контракт должен заранее определить ожидаемые ответы и допустимость раскрытия существования объекта.

## Очистка

Очищай только данные текущего теста и выполняй освобождение ресурсов также при падении. Ошибка очистки не должна скрывать исходную ошибку; её нужно отдельно зафиксировать. Отсутствие данных после неудачного создания и недоступный сервер — разные результаты очистки.

Integration-тесты с изменением схемы или массовой очисткой запускай на отдельной тестовой БД. Наличие URL в конфигурации не разрешает удалять данные внешнего стенда.
