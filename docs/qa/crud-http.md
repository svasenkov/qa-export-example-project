## Коллекция и одиночный ресурс

Примеры формы API, а не список реализованных маршрутов:

- `/api/items` — коллекция; создание элемента часто выполняют через POST, когда URI нового элемента выбирает сервер.
- `/api/items/{id}` — конкретный элемент; известный URI подходит для PUT, если такая операция предусмотрена контрактом.
- `/api/note` — возможный одиночный ресурс текущего пользователя. Для него можно выбрать PUT как создание/замену и не предоставлять POST. Это решение API, а не запрет HTTP.

Наличие `{id}` в пути не определяет допустимость PUT. POST также не ограничен созданием элементов коллекции. [RFC 9110, POST и PUT](https://www.rfc-editor.org/rfc/rfc9110.html#name-post).

## Методы и ответы

- **GET** читает представление ресурса; обычный успешный ответ — `200`.
- **POST** обрабатывает представление согласно семантике целевого ресурса. При создании обычно используют `201` и `Location` нового ресурса.
- **PUT** запрашивает создание или замену состояния известного ресурса. Если создание успешно — `201`; если существующее представление успешно изменено — `200` или `204`. Это не обязанность разрешать создание любого отсутствующего ресурса.
- **PATCH** применяет документ изменений. Формат определяется `Content-Type` и поддержкой сервера; `application/merge-patch+json` — один из форматов, не обязательный тип любого PATCH. Успех может возвращать представление или `204` без тела.
- **DELETE** удаляет связь URI с текущей функциональностью ресурса. Успешный ответ может быть `204`, `200` с представлением результата или `202` при отложенной обработке. Ответ не доказывает физическое удаление всех данных из БД.

`Content-Location` описывает URI представления и не является обязательной заменой `Location` после создания. `409` для PUT допустим при конфликте. Идемпотентность означает одинаковый предполагаемый эффект повторения, а не одинаковые ответы; первый DELETE может дать `204`, следующий — `404`. Источники: [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-methods), [RFC 5789](https://www.rfc-editor.org/rfc/rfc5789.html).

## JSON Merge Patch

Если контракт выбирает JSON Merge Patch, его медиатип — `application/merge-patch+json`. Для объекта:

- пропущенное поле сохраняется;
- переданное значение добавляет или заменяет поле;
- `null` удаляет поле, а не автоматически превращает его в пустую строку;
- вложенные объекты обрабатываются рекурсивно;
- массив заменяется целиком, а не объединяется по элементам;
- `{}` не меняет существующий объект, но сам по себе не определяет статус ответа.

Патч, который не является объектом, заменяет документ целиком. Поэтому `{}` нельзя называть безусловным no-op для любого JSON-значения. Если API допускает только объект с определёнными полями, эти ограничения нужно явно описать и проверить. После применения изменений проверяется допустимость итогового ресурса; запрещённое удаление обязательного поля отклоняется согласно контракту. [RFC 7396](https://www.rfc-editor.org/rfc/rfc7396.html).

## Ошибки и права доступа

Для функции заранее определяются ответы на невалидный JSON, неподдерживаемый медиатип, недопустимое значение, отсутствие ресурса, конфликт и ошибку авторизации. Не выводи полный перечень ошибок только из названия метода.

Для неподдерживаемого формата PATCH предусмотрен `415`; серверу рекомендуется сообщать поддерживаемые форматы через `Accept-Patch`. `400`, `404`, `409`, `412` и `422` относятся к разным причинам; выбирай и проверяй применимые причины, а не требуй все статусы от каждого маршрута. [RFC 5789, обработка ошибок](https://www.rfc-editor.org/rfc/rfc5789.html#section-2.2).

Проверяй владельца, другого пользователя и гостя отдельно. В прежнем задании `/api/note` адресовал собственную заметку пользователя: второй пользователь получал свой ресурс либо отсутствие своего ресурса. Это не равнозначно запросу чужого `/api/items/{id}`. Политику доступа и сокрытия существования объекта необходимо определить для конкретного API.

## Что проверять в CRUD-функции

Выбирай применимые сценарии из требований:

1. Создание и чтение сохранённых значений; выдача идентификатора и адреса по контракту.
2. Замена и частичное обновление: пропущенные поля, `null`, границы, неизвестные поля, вложенные значения — если поддерживаются.
3. Повторные запросы: отсутствие непредусмотренных дубликатов и корректное конечное состояние.
4. Удаление: последующее чтение, повторное удаление и судьба связанных данных.
5. Права доступа: отсутствие чужих данных и запрет изменения чужого ресурса; состояние после отказа не изменилось.
6. Ошибки: статус, тело, заголовки и отсутствие частичного сохранения отвергнутого изменения.
7. Конкурентные изменения и предусловия — если предусмотрены контрактом. Не добавляй ETag или версионирование без потребности задачи.

Unit подходят для правил валидации и преобразований; integration — для реальной БД, ограничений и транзакций; API — для HTTP-контракта и прав доступа. Component/UI проверяют состояния интерфейса, E2E — выбранные сквозные пути. Число E2E определяется риском, а не правилом «ровно один happy path».

Изменяющие тесты используют собственные данные и очистку. Наличие фабрики и teardown не разрешает запуск удаления на prod. Подробности — в [тестовых данных](test-data.md) и [правилах покрытия](testing.md).

## Исторический пример курса

Прежний материал выбирал одну личную заметку `/api/note` с полями `title` и `text`: UI сохранял через PUT и удалял через DELETE, PATCH проверялся на API. Это полезный компактный пример CRUD, но в текущем проекте функция заметки не объявлена реализованной. Её можно выбрать как учебное задание после фиксации требований; перенос справочника сам по себе такого выбора не делает.
