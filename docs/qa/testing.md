# Проверки и покрытие

Смежные темы: [база знаний](README.md), [Page Object и fluent](page-objects.md), [данные и API-клиенты](test-data.md), [результаты и диагностика](test-results.md). Конкретные соглашения ищи по ссылкам в README выбранного модуля.

При проектировании или проверке HTTP CRUD прочитай [справочник CRUD](crud-http.md), затем контракт конкретной функции. HTTP-семантика и условия отдельного учебного задания не взаимозаменяемы.

Языки и инструменты выбирает учащийся в генераторе. [Профиль проекта](../coverage-profile.md) связывает доступные виды тестов с модулями. README и конфигурация этих модулей задают команды, зависимости и соглашения.

## Выбор проверки

Проверяй поведение на уровне, где нужный дефект можно обнаружить достоверно и с приемлемой стоимостью. Термины ниже описывают принятую в проекте классификацию; это не требование иметь отдельный каталог или инструмент для каждого пункта.

- Unit — изолированная логика. Наличие HTTP-объектов в памяти не означает обращение к живому серверу.
- Integration — взаимодействие реальных частей системы, например хранилища и базы данных. Указывай, какие части взаимодействуют; не приписывай тесту проверку обработчика, если он проверяет только хранилище.
- Component — поведение компонента с контролируемыми зависимостями. В некоторых стеках часть проверок фронтенда относится к unit; учитывай назначение конкретного теста.
- API — проверка внешнего API работающего приложения.
- UI — в этом курсе браузерная проверка интерфейса с подменённым API.
- E2E — сквозной пользовательский сценарий через работающие frontend и backend.

Ручные проверки дополняют автоматизацию. Проверки тестовых утилит относятся к качеству самой автоматизации. Smoke — выбранный короткий набор тестов; сравнение изображений — способ проверки. Не вводи из них дополнительные уровни пирамиды.

Способ маркировки тестов зависит от модуля. Аннотация, тег или имя каталога не заменяет чтение того, что тест реально проверяет.

## Что означает «100%» в учебной задаче

До разработки тестов согласуйте конечный перечень требований и сценариев функции, включая существенные отрицательные и граничные случаи. Для каждого запишите ожидаемый результат и подходящую проверку. При изменении требований пересмотрите перечень.

Отдельно учитывайте:

- какие согласованные сценарии имеют содержательные проверки;
- какие из этих проверок действительно выполнены и с каким результатом;
- какие сценарии остаются ручными и кем проверены;
- какие риски и части системы недоступны для оценки.

Если нужен процент покрытия сценариев, указывайте числитель и знаменатель: число сценариев с проверкой / общее число согласованных сценариев. Не уменьшайте знаменатель из-за недоступного уровня или упавшего теста. Неприменимость должна иметь объяснение, а изменение объёма — быть явно согласовано.

Полное покрытие согласованного списка не доказывает полноту самого списка и отсутствие дефектов. Покрытие строк/ветвей кода — отдельная метрика с областью измерения. Результаты тестовых утилит не являются покрытием backend или frontend.

Не требуйте один и тот же сценарий на всех уровнях. Например, API-проверка может проверять ответ на неверный пароль, component-проверка — отображение ошибки, а e2e — доставку ошибки через реальные части системы. Это разные утверждения, если каждое действительно необходимо.

## Доказательства

Для выполненной проверки сохраняй команду, версию проверяемого кода, выбранные тесты, стенд, результат и путь к артефактам. Если git отсутствует, так и укажи; не придумывай commit SHA. При необходимости зафиксируй хеши файлов или идентификатор сборки.

Различай `не запускался`, `выполнен успешно`, `упал`, `пропущен`, `заблокирован средой`. Кешированный результат отмечай отдельно. Наличие отчётов от прошлых запусков не подтверждает текущую попытку.

Для повторных запусков сохраняй отдельные результаты и используй механизм повторного выполнения выбранного раннера. Не удаляй общую папку отчётов, чтобы получить «чистую» статистику.

Manual-чеклист считается выполненным только при наличии результата проверки человеком. Автоматический запуск кода, записывающего текст шагов, подтверждает лишь создание отчёта.

## Стенды и данные

Тесты, которым нужен стенд, используют его конфигурацию из модуля. Для каждого целевого стенда проверь данные, разрешённые операции и зависимости. Переносимость теста между стендами не означает разрешение запускать любые операции на prod.

Unit/component-тесты без внешних зависимостей запускаются без удалённого стенда. Integration-тесты должны явно называть необходимые зависимости и изолированные данные. Подмена недоступной интеграции mock-объектом меняет доказательство, которое даёт тест.
