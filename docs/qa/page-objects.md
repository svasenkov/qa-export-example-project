# Page Object и fluent

Page Object предоставляет тесту операции страницы, скрывая детали поиска элементов. Повторяющиеся части интерфейса можно представить отдельными объектами компонентов. Эти объекты относятся к автоматизации и не обязаны повторять внутреннюю структуру frontend.

## Ответственность

Тест задаёт сценарий и ожидаемый результат. Страница или компонент выполняет действия с интерфейсом и предоставляет наблюдаемое состояние. Локаторы принадлежат странице или компоненту; общую шапку не нужно копировать в каждую страницу.

Расположение утверждений — явно выбранное соглашение модуля. [Документация Selenium](https://www.selenium.dev/documentation/test_practices/encouraged/page_object_models/) рекомендует оставлять проверки результата в тесте, а в Page Object проверять готовность страницы. Текущий Java-модуль использует другой вариант: методы `should…` внутри страниц с переданным из теста ожиданием. Это соглашение проекта, а не универсальное требование паттерна.

Проверка состояния не должна выполнять навигацию или менять данные, чтобы добиться ожидаемого результата. Объект следующей страницы сам по себе не доказывает, что переход состоялся: нужна проверка наблюдаемого состояния.

## Fluent API

Fluent API делает вызовы читаемыми в терминах сценария. Цепочки методов — один из способов его реализации.

- Действие без перехода может возвращать текущую страницу.
- Действие с переходом может возвращать объект следующей страницы.
- Успешный и неуспешный сценарии должны различать ожидаемую страницу.
- Метод чтения состояния может возвращать значение; метод завершённого действия может не иметь возвращаемого значения.

Fluent не требует запрета `void` или объединения всего теста в одну строку. В асинхронном стеке учитывай `await` и тип результата; механическое копирование Java-цепочек может дать неверный код.

## Локаторы и ожидания

Используй устойчивые признаки элемента, предусмотренные приложением и инструментом: доступное имя/роль, стабильный идентификатор или согласованный `data-testid`. Выбор фиксируется в модуле. Не привязывай тест к случайному CSS-классу или позиции элемента, если позиция не является предметом проверки.

Одинаковые элементы ограничивай областью нужного компонента. Ожидай конкретное состояние средствами раннера; фиксированная пауза не подтверждает готовность. После изменения локатора проверь причину исходного падения и соответствие новому интерфейсу.

Примеры конкретного проекта находятся в документации его тестового модуля. Официальные примеры: [Selenium Page Objects](https://www.selenium.dev/documentation/test_practices/encouraged/page_object_models/) и [Selenide Page Objects](https://selenide.org/documentation/page-objects.html).
