# Соглашения Java-автоматизации

Это соглашения текущего модуля JUnit / Rest Assured / Selenide, а не обязательные правила для всех стеков генератора. Общие объяснения — в [базе знаний](../../../docs/qa/README.md), команды — в [README](README.md).

## Страницы, компоненты и fluent

Страницы находятся в [pages](src/test/java/pages), общая шапка — в [HeaderComponent](src/test/java/pages/components/HeaderComponent.java) и доступна через `BasePage.header`. Переиспользуй эти объекты. Не создавай драйвер и не дублируй локаторы в сценарии.

В [LoginPage](src/test/java/pages/LoginPage.java) методы заполнения возвращают `LoginPage`, успешная отправка — `HomePage`, отправка с ожидаемой ошибкой — `LoginPage`. Проверки `should…` возвращают текущую страницу. Пример вызовов существующих методов, где `username` и `password` — данные подготовленного пользователя:

```java
new LoginPage()
        .openPage()
        .fillAndSubmitForm(username, password)
        .shouldBeOpen()
        .shouldHaveWelcomeMessage("Welcome, " + username + "!");

new LoginPage()
        .openPage()
        .typeUsername(username)
        .typePassword(wrongPassword)
        .submitExpectingError()
        .shouldHaveErrorMessage("Wrong login or password");
```

Это фрагменты сценариев, не готовые тесты: lifecycle и конфигурацию предоставляет [TestBase](src/test/java/tests/TestBase.java). Во втором примере требуется существующий пользователь и заведомо неверный пароль.

Возврат `new HomePage()` не проверяет успешность входа. Сценарий обязан подтвердить нужное наблюдение. `should…` не выполняют навигацию для исправления состояния. `void` допустим для технических операций и cleanup — например, он уже используется в `BasePage` и `AuthApiClient`.

## Локаторы

Текущие страницы используют `data-testid`, согласованные с frontend. Локаторы хранятся в страницах/компонентах; повторяющиеся элементы ограничиваются своим контейнером. Поле `private final SelenideElement` удобно для повторного использования, но единичный локатор внутри Page Object тоже уже используется в этом модуле.

Проверяй соответствие реальной разметке. Для готовности используй `shouldBe` / `shouldHave` с необходимым условием; `Thread.sleep` не заменяет ожидание состояния. Изменение селектора следует за диагностикой причины падения.

## API и данные

[AuthApiClient](src/test/java/api/AuthApiClient.java) предназначен для успешной подготовки и очистки: `register` требует `201`, `login` — `200`, `deleteAccount` — `204`. Отрицательную API-проверку нельзя строить на helper, который заранее утверждает успех. Следуй существующим API-тестам и [ApiTestBase](src/test/java/api/ApiTestBase.java).

Создавай собственные аккаунты для изменяющих сценариев. Не удаляй `user1` и не связывай тесты порядком выполнения. `deleteAccountQuietly` сейчас подавляет ошибки очистки; его вызов не доказывает, что аккаунт удалён. Для дипломной версии требуется отдельно наблюдаемый результат cleanup.

## Allure

Существующие страницы используют `@Step` для пользовательских действий и проверок. Сохраняй читаемый сценарий, избегай дублирования через `Allure.step` вокруг того же действия. Обязательность `@Step` на любом публичном техническом методе не вводится.

Пароли и токены не должны попадать в отчёт. Одного отсутствия `{password}` в тексте аннотации недостаточно: проверь параметры и вложения реального отчёта. Текущий исходный код ещё не подтверждает их безопасную публикацию. Перед публикацией требуется отдельная проверка артефактов.

## Стенды и границы доказательств

Явно выбирай `-Denv=ci` для локального живого приложения и `-Denv=mock` для UI с подменённым API. Mock-проверка не подтверждает работу backend. API-helper для подготовки E2E не делает весь сценарий проверкой регистрации через UI.

Результат unit/infra-проверки Java-утилиты не является покрытием Go-продукта. Ручной чеклист, записанный тестом в Allure, не является ручным выполнением. Ссылки на команды и отчёты находятся в [README](README.md).
