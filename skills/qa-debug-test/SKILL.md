# Диагностика теста

Прочитай [профиль](../../docs/coverage-profile.md), README нужного модуля, сам тест и относящиеся к падению результаты. Команды и способ изоляции зависят от раннера выбранного стека.

- Установи точку отказа: настройка среды, сборка, подготовка данных, выполнение или проверка результата. Ошибка до запуска теста не доказывает дефект его сценария.
- Зафиксируй команду, выбранные тесты, версию проверяемого кода, стенд и доступные сообщения об ошибке. Не публикуй секреты и лишние данные из логов.
- Сопоставь ожидание теста с требованием или контрактом. Не считай ожидание неверным только потому, что реализация возвращает другое значение.
- Для воспроизведения выбери минимальный тест. Перед повтором проверь, безопасны ли повторные операции с данными. Убедись, что раннер действительно выполняет тест заново.
- Для исследования нестабильности задай ограниченное число попыток, достаточное для текущей гипотезы. Сохрани результат каждой попытки. Несколько успешных запусков не доказывают отсутствие flaky-поведения.
- Раздели наблюдение, гипотезу и проверку гипотезы. Если данных недостаточно, назови недостающие данные вместо выдуманной причины.
- Если проверка сверяет результат с хранимым эталоном (скриншот, golden-файл, снапшот, запись контракта), различай три причины расхождения: изменение продукта, устаревший эталон и различие среды. Устаревание эталона доказывай его содержимым — например, эталон записан для другой версии или конфигурации продукта, — а не только фактом несовпадения. Перегенерация эталона — отдельное согласованное действие командой модуля; после неё сравнение выполняется заново.
- Сверяй пины окружения и исполнителей: закреплённые версии браузера, рантайма, сервисов, профили каталогов эталонов и параметры вызова. Несовпадение пина с фактической средой даёт падение без дефекта продукта — исправляй выбор среды или пин по конфигурации модуля, а не ожидание теста.
- Для проверок, завязанных на контракт и разметку (локаторы, поля ответа, заголовки), сверяй точку отказа с актуальным контрактом и реализацией. Соседний тест и его селектор или клиент — не источник истины.
- Если пользователь запросил только triage, закончи диагнозом. Если исправление разрешено и причина установлена, внеси минимальную правку и выполни проверку, способную обнаружить исходный дефект.

Не скрывай падение отключением теста, ослаблением проверки, необоснованным увеличением таймаута или обновлением эталона. Для изменения ожидаемого поведения нужно основание в требованиях.

Результат: причина с доказательствами либо оставшиеся гипотезы; при исправлении — изменение и результат проверки. Отдельно укажи, что не удалось воспроизвести или выполнить.
