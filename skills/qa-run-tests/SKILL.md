# Запуск тестов

Прочитай [профиль](../../docs/coverage-profile.md) и README модуля выбранных тестов. Стек тестов может отличаться от стека продукта.

1. Определи выбранные пользователем тесты, модуль и, если нужен, стенд. Если объём не задан, выбери минимальную проверку, отвечающую запросу, и назови её до запуска.
2. Проверь наличие раннера, зависимостей, конфигурации и необходимых сервисов. Прочитай фактический стенд по умолчанию: команда без параметров может обращаться к prod. Выбери стенд явно средствами этого модуля; без соответствующего запроса не запускай тесты на внешнем стенде. Не считай наличие URL доказательством доступности. Запуск существующих тестов сам по себе не требует `access: write`, но может менять данные стенда; `access: none` не разрешает обращения к недоступной поверхности.
3. Возьми команду из README модуля и сверь с конфигурацией раннера. Для отдельного теста используй поддерживаемый им фильтр; не переноси синтаксис из другого раннера. Если есть режим проверки выбора без выполнения, используй его, когда выбор неоднозначен.
4. Выполни согласованный запуск. Не меняй код, ожидания или эталонные изображения ради зелёного результата. При недоступной зависимости сообщи конкретный блокер.
5. Проверь не только exit code: какие тесты выбраны, сколько выполнено, упало и пропущено; не использован ли кеш вместо нового выполнения. Ноль выполненных тестов не подтверждает проверку.
6. Различай статусы результата: `pass`, `fail`, `skip`, `blocked` (недоступный ресурс или отсутствующее разрешение), `not_run`. Skip и blocked не считай pass и не смешивай в числителе.

Если для запуска нужен локальный Compose-стенд, а общий стенд уже занят другим checkout или внешним наблюдателем, не переиспользуй его и не пересоздавай чужие контейнеры: выбери собственные compose project name, порты, теги образов и volumes и проверь `container_name` и другие ресурсы, которые обходят изоляцию по project name. Работающий контейнер с подходящим портом не доказывает принадлежность этому checkout — сверь mounts и image tag. Не останавливай чужой watchdog и чужие сервисы.

Зафиксируй идентичность прогона: ревизия исходников и dirty diff, версии инструментов, конфигурация, image IDs, версия браузера и driver, адреса стенда. Результаты каждой попытки сохраняй в новый каталог или файл, не перезаписывая прежние отчёты. Если связываешь результат с исходниками, тестами, конфигурацией и параметрами runtime, используй `tools/quality` begin/check — см. [tools/quality README](../../tools/quality/README.md).

Результат: модуль, команда без секретов, стенд или отсутствие необходимости в нём, exit code, фактические результаты со статусами и путь к отчёту. Если команда не запускалась — скажи это явно.

Для ручных сценариев запуск генератора отчёта не является выполнением проверки человеком; правила учёта — в [testing.md](../../docs/qa/testing.md).
