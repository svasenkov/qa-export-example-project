# Учебный QA-проект

Это сборка с выбранными backend, frontend и автоматизацией. Выбор модулей и доступ к ним записаны в [профиле](docs/coverage-profile.md). В другой сборке языки и инструменты могут отличаться; общие инструкции и skills от них не зависят.

Модули текущей сборки:

- [Backend](backend/go/backend-go-stdlib/README.md).
- [Frontend](frontend/typescript/frontend-typescript-vue/README.md).
- [Автотесты API/UI/E2E](tests/java/tests-java-junit5-rest_assured-selenide/README.md).

Зависимости, команды тестов и способы выбора отдельной проверки описаны в README соответствующего модуля. Проверяйте их вместе с конфигурацией раннера.

## Локальное приложение

Если на компьютере уже работает autotests.ai, используй отдельный проект Compose и локальные порты дипломного примера:

```bash
docker compose -p qa-diploma --env-file .env.diploma.example up -d --build
curl -fsS http://127.0.0.1:18831/api/health
```

UI: `http://127.0.0.1:19821/`. Для mock добавь к той же команде Compose `--profile mock up -d --build stand-gateway`; gateway будет на `http://127.0.0.1:19911/`. Файл [.env.diploma.example](.env.diploma.example) содержит только локальные порты. Имя `qa-diploma` отделяет контейнеры, сеть и volume от существующей сборки. Проверь, что выбранные порты свободны.

Для тестов обязательно переопредели адреса: `-Denv=ci -DbaseUrl=http://127.0.0.1:19821 -DapiBaseUrl=http://127.0.0.1:18831/`. Для UI с mock используй `-Denv=mock -DbaseUrl=http://127.0.0.1:19911 -DapiBaseUrl=http://127.0.0.1:19911/`. Иначе тесты могут попасть на другую сборку с портами по умолчанию.

Остановка отдельного примера: `docker compose -p qa-diploma --env-file .env.diploma.example down`. Без `-v` данные БД сохраняются. Не удаляй volume, пока его данные нужны.

### Порты по умолчанию

Следующие команды применимы, если имя Compose и порты не заняты другой сборкой.

Из корня проекта:

```bash
docker compose up -d --build
curl -fsS http://localhost:8831/api/health
```

UI с живым backend доступен через gateway `http://localhost:9821/`.
Прямой frontend-порт `9813` не заменяет gateway для обращения к API.

Для браузерных тестов с подменённым API:

```bash
docker compose --profile mock up -d --build stand-gateway
```

Mock gateway по умолчанию использует порт `9911`. Источник конфигурации — [docker-compose.yml](docker-compose.yml); при переопределении портов согласуйте с ними конфигурацию тестов.

## Работа с агентом

В [базе знаний QA](docs/qa/README.md) описаны Page Object, fluent, тестовые данные, API-клиенты и диагностика. Детали выбранного стека находятся в документации соответствующего модуля.

Единственный каталог процедур — `skills/`. [AGENTS.md](AGENTS.md) содержит общие инструкции и ссылки на четыре процедуры: запуск, диагностику, добавление теста и аудит покрытия. [testing.md](docs/qa/testing.md) определяет, какие доказательства нужны для покрытия требований. [harness-checks.md](docs/qa/harness-checks.md) содержит проверку подключения и контрольные задания для самого агента.

```bash
python3 -B tools/check_harness.py
python3 -B -m unittest discover -s tools -p 'test_*.py'
```

Эти команды проверяют метаданные skills, локальные ссылки и сам инструмент проверки. Они не запускают продуктовые тесты и не подтверждают поведение агента.

## Git hooks

Проверки перед коммитом лежат в [.githooks/pre-commit](.githooks/pre-commit). Git не подхватывает их из репозитория автоматически — после клонирования включи один раз:

```bash
git config core.hooksPath .githooks
```

Хук выполняет `python3 -B tools/check_harness.py`, unit-тесты `tools/` и поиск типовых форматов секретов в staged-файлах. Продуктовые тесты модулей он не запускает и их результат не подтверждает. Осознанный обход в исключительном случае: `git commit --no-verify`.

## Следующая функция

Цель полной учебной версии, критерии готовности и подход к сокращённым заданиям описаны в [дипломном проекте](docs/diploma.md). Текущая сборка ещё не является завершённым образцом.

Сначала согласуйте поведение функции и её сценарии. После реализации сопоставьте сценарии с подходящими тестами доступных модулей, добавьте недостающие проверки и выполните их. «100%» относится к явно согласованному списку сценариев; покрытие кода и результаты выполнения учитываются отдельно.

В этой сборке нет корневого GitHub Actions workflow. Локальный запуск compose и тестов не доказывает наличие или успешный запуск CI. Для настройки CI требуется отдельная задача с реальной конфигурацией выбранного раннера.
