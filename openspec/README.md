# Требования и изменения

OpenSpec хранит согласованные требования и изменения к ним. Начальная база
перенесена из прежнего описания `login-flow` v0.9 без изменения поведения приложения.
Ссылки на тесты и ограничения доказательств находятся в [auth-checks.md](../docs/qa/auth-checks.md).
Карта переноса и результаты проверки сохранены в
[архиве миграции](changes/archive/2026-10-17-migrate-requirements/verification.md).

## Источники

- [authentication](specs/authentication/spec.md) — вход и неверные учётные данные (`AUTH-*`).
- [registration](specs/registration/spec.md) — регистрация и занятое имя (`REG-*`).
- [account](specs/account/spec.md) — профиль, сессия, выход и удаление (`ACC-*`).
- [auth-forms](specs/auth-forms/spec.md) — общие проверки полей и ошибки (`FORM-*`),
  включая [точные сообщения](specs/auth-forms/messages.md).
- [OpenAPI](../docs/api/openapi.yaml) — машиночитаемый HTTP-контракт.
- [UI-соглашения](../frontend/typescript/frontend-typescript-vue/docs/auth-ui.md) —
  атрибуты элементов и подключение дизайн-системы выбранного frontend.
- [Проверки и покрытие](../docs/qa/testing.md) — правила доказательств.

OpenAPI пока не описывает все ограничения и ошибки из сценариев форм. Миграция
сохраняет его существующую HTTP-схему; расширение её полноты — отдельная задача.
При расхождении источников сначала установите ожидаемое поведение, не меняйте
требования автоматически по реализации. Наличие спеки не подтверждает её соблюдение.

## Структура

`specs/<capability>/spec.md` — действующие требования. Дополнительные файлы рядом
хранят нормативные детали, например тексты сообщений. `changes/<change>/` —
предлагаемое изменение: `proposal.md`, `specs/` с дельтами, `design.md`, `tasks.md`.
Завершённые изменения хранятся в `changes/archive/`.

Capability описывает устойчивую возможность, а не язык реализации, отдельный тест
или имя агента. Общие правила форм вынесены отдельно, чтобы вход и регистрация
не имели расходящихся копий. ID требований и сценариев сохраняйте при редактуре;
новым сценариям назначайте новые ID, удалённые не переиспользуйте.

`agents/` и `eval/` подготовлены для следующего этапа:
[назначение агентов](../agents/README.md), [оценка их работы](../eval/README.md).
Их будущее поведение можно описывать отдельными capability без переноса продуктовых
спецификаций или тестов в эти каталоги.

## Работа над изменением

Используйте закреплённый локальный CLI: установка и команды — в
[tools/openspec](../tools/openspec/README.md). Глобальная установка не нужна.

1. Прочитайте профиль проекта, затронутые спеки и README модулей.
2. Для изменения поведения создайте change и заполните предложение, дельты,
   техническое решение и задачи. `MODIFIED` содержит полное требование со всеми
   сценариями; частичная замена теряет остальные сценарии при архивации.
3. Сверьте предложение с заданием. Если поведение ещё не согласовано, получите
   решение до реализации. Уже данное разрешение в текущем задании действует;
   OpenSpec не добавляет обязательного повторного согласования.
4. Реализуйте задачи, используя существующие QA-skills. Выполните подходящие
   проверки, сохраните результаты отдельно от требований и обновите связи с тестами.
5. Проверьте структуру OpenSpec. После завершения задач архивируйте change с
   переносом дельт в основные спеки; проверьте получившийся diff и ссылки.

Дельта-операции относятся к требованиям в `spec.md`. Дополнительные файлы вроде
`messages.md`, OpenAPI и UI-соглашений меняются явно в той же работе; archive
не синхронизирует их автоматически. Согласуйте их с дельтой и проверьте diff.

Небольшое исправление реализации без изменения требований не требует выдуманной
дельты. Для отдельного tooling/docs change используйте `skip_specs: true` в
`.openspec.yaml`; при архивации такого change — `--skip-specs`.

## Что подтверждают проверки

`validate` проверяет структуру спецификаций. Отметки в `tasks.md` и архивация
не заменяют тесты, ревью и ручные проверки. Результаты продуктовых тестов и будущих
eval учитываются отдельно. Git commit, push и публикация не являются частью
архивации и выполняются только в разрешённом объёме задания.
