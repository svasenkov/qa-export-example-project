# Проверка покрытия

Прочитай [профиль](../../../docs/coverage-profile.md), [правила покрытия](../../../docs/qa/testing.md), требования выбранной функции и относящиеся к ней тесты. Не ограничивай поиск аннотациями или каталогами одного языка.

1. Зафиксируй границы: функция, версия требований, сценарии и существенные риски. Если перечень требований неполон, отметь это; не заявляй процент покрытия без определённого основания для расчёта.
2. Для каждого сценария найди проверки и прочитай их утверждения. Название теста, тег или наличие файла сами по себе не доказывают проверку требования.
3. Укажи уровень, модуль и конкретный тест; отдельно — последний подходящий результат запуска, если он доступен. Старый запуск другой версии или другого стенда не подтверждает текущий результат.
4. Различай отсутствие проверки, невозможность проверить из-за доступа, неприменимость уровня и отсутствие доказательств выполнения. `access: none` не является разрешением писать тесты и не доказывает покрытие за пределами доступного проекта.
5. Рассмотри все уровни, предусмотренные профилем, включая integration. Не требуй каждый сценарий на каждом уровне и не подменяй нижние уровни большим количеством e2e.
6. Сформулируй только подтверждённые пробелы и приоритеты по риску. Ноль находок допустим. Для каждого предлагаемого теста укажи проверяемое поведение, уровень, доступный модуль и необходимые условия запуска.

Результат: сопоставление «требование → тест → доказательство → пробел», ограничения аудита и план. Для ручных проверок требуется результат человека, а не успешная генерация чеклиста. Не запускай тесты и не реализуй план, если пользователь запросил только анализ.
